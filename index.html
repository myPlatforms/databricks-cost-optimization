주어진 예산으로 최대 가치를 — 비용 효율은 비즈니스 목표와 ROI에서 출발합니다
01

최적 리소스 선택

비즈니스 목표와 워크로드 성능에 맞는 리소스를 고릅니다. 새 워크로드는 배포 옵션을 비교해 가격 대비 성능이 가장 좋은 것을 선택합니다.

02

리소스 동적 할당

성능 요구에 맞춰 할당하고 해제합니다. 유휴·저활용 리소스는 찾아서 재구성·통합하거나 끕니다.

03

비용 모니터링·통제

비용 = 소비량 × 단가. 리소스별로 모니터링해 기준선을 만들고, 워크로드 소유자에게 비용을 배분해 ROI를 측정합니다.

04

비용 효율적 워크로드 설계

사용량·성능 지표로 시작 규모를 정하고 오토스케일링을 씁니다. 변동이 큰 워크로드는 작은 인스턴스로, scale-up보다 scale-out을 우선합니다.

네 원칙은 한 번으로 끝나지 않습니다 — 규모 확대·신규 프로젝트·비용 급증 때마다 다시 점검하는 지속적 과정입니다

04
① 최적 리소스 선택 — 워크로드에 맞는 엔진
같은 작업도 어떤 컴퓨트에서 돌리느냐에 따라 비용이 크게 달라집니다

Delta Lake

Parquet·ORC·JSON보다 빠른 성능 최적화 형식. Job compute라면 실행 시간 단축이 곧 비용 절감입니다.

Job compute

비대화형 작업은 All-purpose보다 훨씬 저렴합니다. 멀티태스크 잡은 태스크 간 컴퓨트를 재사용해 기동 시간이 한 번만 듭니다.

SQL Warehouse

대화형 SQL에 가장 비용 효율적인 엔진. Photon 기본, Serverless는 IWM(intelligent workload management)으로 대량 쿼리를 빠르게 처리합니다.

최신 런타임

정기 릴리스마다 성능이 개선되고, 효율이 좋아진 만큼 비용이 줄어드는 경우가 많습니다.

GPU는 필요한 곳에만

GPU 가속 라이브러리를 쓰는 워크로드가 아니면 이득이 없습니다. 관리자가 GPU 인스턴스를 제한할 수 있습니다.

Photon 평가

코드 수정 없이 켜는 벡터화 엔진. 정기 잡은 더 빠른지뿐 아니라 더 싼지도 확인합니다.

Serverless · BI

Non-serverless SQL Warehouse는 기동에 수 분이 걸려 유휴 시간에도 켜 두는 경우가 많습니다. Serverless는 수 초 안에 기동·확장하므로 즉시 응답과 유휴 종료를 함께 얻고, 축소도 더 일찍 합니다.

Serverless · Model Serving

요청량 변화에 맞춰 자동으로 확장·축소해 인프라 비용을 줄이면서 지연 시간을 유지합니다.

06
② 리소스 동적 할당
쓰는 만큼만 켜고, 안 쓰면 끈다

오토스케일링

계산량이 많은 구간에만 워커를 늘리고 끝나면 줄입니다. 고정 크기보다 전체 비용이 낮아집니다.

Structured Streaming은 축소에 제약이 있어 Lakeflow pipelines의 enhanced autoscaling을 권장합니다.

Auto termination

모든 대화형 컴퓨트에 유휴 종료를 설정합니다. 업무 시간에만 쓴다면 아침에 스케줄로 재기동하고 CACHE SELECT로 데이터를 미리 올려 둡니다.

Pool

기동이 너무 길면 유휴 인스턴스 풀을 씁니다. 풀에서 대기하는 인스턴스에는 DBU가 청구되지 않지만, 클라우드 인스턴스 비용은 발생합니다.

컴퓨트 정책

  • 오토스케일 + 최소 워커 수
  • 합리적인 auto termination (예: 1시간)
  • 비용 효율적인 인스턴스만 허용
  • 스팟 인스턴스 전략 적용

③ 비용 모니터링·통제
설정(Setup) → 모니터링(Monitoring) → 관리(Management)
Setup

태깅은 처음부터

  • 최소 Business Units · Projects, 필요하면 Environment
  • 워크스페이스·클러스터·SQL Warehouse·풀에 태그 → 사용 로그와 클라우드 리소스로 전파
  • 태그는 과거 사용분에 소급할 수 없어 처음에 넉넉히 설계
Monitoring

예산과 가시성

  • Budgets + 이메일 알림, usage policy로 Serverless 사용량 귀속
  • 계정 콘솔 비용 관리 AI/BI 대시보드
  • system.billing.usage 시스템 테이블
  • OpenSharing egress 비용 모니터링
  • Account REST API로 사용량 CSV 다운로드
Management

조직 차원의 관리

  • 태그를 적용·정리하는 housekeeping 잡 (변경은 감사 로그로)
  • 정기 비용 감사, 월간 비용 리포트 공유
  • 팀별 비용 영향 교육
  • 컴퓨트 정책으로 유형·크기 통제
총비용 = DBU + VM · 디스크 · 네트워크 — 단, Serverless는 VM 비용이 이미 DBU에 포함됩니다

Streaming

상시 실행 vs 트리거 실행

실시간 수집이라도 분석에 필요한 신선도가 몇 시간·하루 단위라면, 하루 몇 번 실행으로 충분합니다. 24시간 켜 둘 이유가 없습니다.

저지연이 필요 없는 증분 작업은 Structured Streaming의 AvailableNow 트리거(증분 배치)를 권장합니다.

Spot

온디맨드 vs 스팟

스팟은 클라우드의 여유 자원을 싸게 쓰는 방식입니다. 첫 인스턴스(드라이버)는 항상 온디맨드로 두고, 스팟 회수로 조금 늦어져도 괜찮은 워크로드에 씁니다.

Fleet 인스턴스 타입을 쓰면 가격과 가용성이 가장 좋은 물리 인스턴스를 Databricks가 골라 줍니다.
